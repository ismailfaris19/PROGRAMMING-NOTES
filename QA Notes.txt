//////////////////////////////////// TESTING NOTES ////////////////////////////////////

@ What is software testing?

    > Software testing is the process of checking whether an application works as expected and identifying defects before the application reaches end users.

    > Example: In a login page, we test whether valid credentials allow a user to log in and invalid credentials display an appropriate error message.

    > Interview answer: Software testing helps verify that an application meets its requirements, works correctly, and delivers quality to users.


@ What is the difference between manual testing and automation testing?

    > Manual testing	
        >> Test cases are executed by a person.	
        >> Usually takes more time for repetitive tests.	
        >> No automation code is required.	
        >> Useful for exploratory and usability testing.	
        >> Can be more prone to human execution errors.	

    > Automation testing
        >> Test cases are executed using scripts and tools.
        >> Faster for repetitive tests.
        >> Requires programming or scripting skills.
        >> Useful for regression and repetitive testing.
        >> Provides consistent execution when scripts are reliable.

    > Example:
        >> Manual: A tester checks the login page by entering credentials.
        >> Automation: A Playwright script enters credentials, clicks Login, and verifies the dashboard.


@ What is the difference between QA, QC, and testing?

    > QA: Establishing coding standards and a testing process.

    > QC: Reviewing whether the delivered application meets quality requirements.

    > Testing: Checking whether the login functionality works correctly.

    > Interview answer: QA focuses on preventing defects through better processes, QC focuses on checking product quality, and testing is an activity used to evaluate the software and identify defects.


@ What is the Software Testing Life Cycle (STLC)?

    > STLC is a sequence of activities performed by the testing team to ensure software quality.

    > The main phases are:

        1) Requirement Analysis: Understand requirements and identify what can be tested.

        2) Test Planning: Define scope, resources, tools, schedule, and approach.

        3) Test Case Development: Prepare test scenarios, test cases, and test data.

        4) Test Environment Setup: Prepare the required hardware, software, browsers, and data.

        5) Test Execution: Execute tests, compare actual and expected results, and log defects.

        6) Test Closure: Summarize results, defect status, coverage, and lessons learned.


@ What are the different levels of testing?

    > There are four main testing levels:

        >> Unit Testing: Tests an individual function or component.
            - Example: Testing a function that calculates a discount.

        >> Integration Testing: Tests whether multiple modules or services work together.
            - Example: Verifying that the frontend sends data correctly to an API.

        >> System Testing: Tests the complete application as a whole.
            - Example: Testing an end-to-end shopping flow.

        >> Acceptance Testing: Checks whether the software meets business requirements and is ready for acceptance.
            - Example: A business user verifies the checkout process before release.


@ What is the difference between severity and priority?

    > Severity:	
        
        >> Measures the impact of a defect on the system.	
        
        >> Usually assessed by QA with technical and business input.	
        
        >> Focuses on impact.	

    > Priority:
        
        >> Measures how urgently the defect should be fixed.
        
        >> Usually agreed with product, development, and business stakeholders.
        
        >> Focuses on urgency.

    > Interview answer: Severity tells us how serious a defect is, while priority tells us how soon it needs to be fixed. They are related, but they are not the same.


@ What is the difference between verification and validation?

    > Verification	
        
        >> Checks whether we are building the product correctly.	
        
        >> Focuses on requirements, design, specifications, and implementation artifacts.	
        
        >> Often includes reviews and inspections without executing the software.	

    > Validation
        
        >> Checks whether we are building the correct product.
        
        >> Focuses on whether the actual software meets user needs.
        
        >> Commonly includes executing tests on the software.


@ What is a test case, test scenario, and test plan?

    > Test scenario: A high-level feature or situation to test.	
        >> Verify login functionality.

    > Test case: Detailed steps, preconditions, test data, and expected result.	
        >> Enter valid credentials, click Login, and verify the dashboard.

    > Test plan: Document describing the overall testing scope, approach, resources, schedule, and risks.
        >> Plan testing for the upcoming release.

    > A sample test case:
        - Test Case ID: LOGIN_001
        - Scenario: Login with valid credentials.
        - Precondition: User account exists.
        - Steps: Open login page, enter valid credentials, click Login.
        - Expected result: User is redirected to the dashboard.


@ What is a test strategy?

    > A test strategy is a high-level approach that defines how testing will be performed to achieve quality objectives.

    > It can cover:
        - Testing levels and types.
        - Manual and automation approaches.
        - Tools and frameworks.
        - Test environments and data.
        - Risk management.
        - Entry and exit criteria.
        - Reporting and defect management.

    > Example: A strategy might specify using Playwright for browser-based regression tests, API tests for service validation, and performance testing tools for load testing.

    > Test plan vs. test strategy: A test strategy describes the overall testing approach; a test plan explains how testing will be organized and executed for a particular project or release. In practice, terminology and document structure vary by organization.


@ What is the difference between positive and negative testing?

    > Positive testing	
        
        >> Checks expected behavior with valid inputs.
        
        >> Confirms valid operations succeed.

    > Negative testing
        
        >> Checks how the application handles invalid or unexpected inputs.
        
        >> Confirms invalid operations are rejected or handled safely.

    > Example — Login:
        - Positive: Enter a valid email and password; verify successful login.
        - Negative: Enter an invalid password; verify an appropriate error message.
        - Additional negative cases: Empty fields, invalid email format, or expired session.


@ What is Boundary Value Analysis (BVA)?

    > Boundary Value Analysis is a test design technique that focuses on values at the edges of an allowed range because defects often occur at boundaries.

    > Example: An age field accepts values from 18 to 60 inclusive.

        Test value	Expected result
        17	        Invalid
        18	        Valid
        19	        Valid
        59	        Valid
        60	        Valid
        61	        Invalid

    > Interview answer: BVA helps identify boundary-related defects by testing values at, just below, and just above the allowed limits.


@ What is Equivalence Partitioning?

    > Equivalence Partitioning divides input data into groups expected to behave similarly. Instead of testing every possible value, we select representative values from each group.

    > Example: An age field accepts values from 18 to 60.

        Equivalence partition
        Below 18 — invalid
        18–60 — valid
        Above 60 — invalid

    > Difference from BVA:
        - Equivalence Partitioning tests representative values from each group.
        - Boundary Value Analysis tests values near the group edges.


@ Types of Software Testing:

    1. Smoke Testing:	

        > Checks whether the main features of a new build are working.	

        > After deploying an application, check whether it opens, login works, and the dashboard loads.

    2. Sanity Testing:

        > Checks whether a specific change or bug fix works correctly.	

        > After fixing a password-reset bug, test the password-reset functionality.

    3. Regression Testing:	

        > Checks whether existing features still work after code changes.	

        > After updating the checkout page, verify that login, cart, coupon, and payment features still work.

    4. Exploratory Testing:	

        > Tests the application freely without following predefined test cases, using experience and curiosity to find defects.	

        > Try different inputs, click buttons in unusual sequences, and navigate quickly to discover unexpected issues.

    5. Functional Testing:	

        > Checks whether features work according to the requirements.	

        > Enter valid login credentials and verify that the user reaches the dashboard.

    6. Performance Testing or Non-Functional Testing:	

        > Checks the application's speed, stability, and responsiveness under different workloads.	

        > Simulate 1,000 users accessing a website at the same time and check response times and errors.


@ What is risk-based testing?

    > Risk-based testing prioritizes testing based on the likelihood of a failure and the impact that failure would have.

    > Example: In an e-commerce application:
        - Payment processing — high priority because failures can cause financial loss.
        - Login and authentication — high priority because failures can block users or create security risks.
        - A minor decorative icon — usually lower priority.

    > Interview answer: Risk-based testing helps us focus testing effort on the features most likely to fail or cause serious business impact, especially when time is limited.


@ When should a test case be automated?

    > A test case is a good candidate for automation when it is:
        - Repeated frequently.
        - Part of the regression suite.
        - Stable enough to automate reliably.
        - Time-consuming to execute manually.
        - Data-driven and needs many input combinations.
        - Important to business operations.
        - Required across multiple browsers or environments.
        - Suitable for repeatable, objective verification.

    > Example: Automating login, registration, checkout, and frequently repeated regression scenarios can save significant execution time.

    > Automation may be less suitable for one-time tests, highly unstable features, subjective usability checks, or exploratory testing that requires human judgment.


@ What types of automation frameworks do you know?

    > Common automation framework approaches include:

        >> Linear / record-and-playback =>	Executes recorded or sequential steps.
        >> Modular => Divides tests into reusable modules.
        >> Data-driven => Runs the same test with different data sets.
        >> Keyword-driven => Uses keywords to represent actions.
        >> Hybrid => Combines multiple approaches.
        >> BDD => Organizes scenarios around business-readable Given/When/Then steps.
        >> Page Object Model (POM) => Separates page locators and page actions from test cases.

    > Interview answer: I am familiar with data-driven, modular, hybrid, BDD, and Page Object Model approaches. With Playwright, I can use POM, fixtures, reusable utilities, and parameterized tests to build a maintainable framework.


@ The Defect Life Cycle:

    > The Defect Life Cycle (also known as the Bug Life Cycle) is the specific sequence of states that a defect passes through from its initial discovery until it is resolved, verified, and officially closed.

    > Standard Defect Life Cycle Flow:

        Plaintext
        [NEW] ───▶ [ASSIGNED] ───▶ [OPEN] ───▶ [FIXED] ───▶ [PENDING RETEST] ───▶ [RETEST]
                        │                           │                                  │
                        ▼                           │                                  ├──▶ [VERIFIED] ──▶ [CLOSED]
              ┌───────────────────┐                 │                                  │
              │ Rejected /        │                 │                                  └──▶ [REOPENED] ──┐
              │ Duplicate /       │                 │                                          ▲         │
              │ Deferred /        │                 └──────────────────────────────────────────┴─────────┘
              │ Not a Defect      │
              └───────────────────┘


    > Step-by-Step Defect States:

        1. New: When a tester identifies an anomaly, unexpected behavior, or discrepancy against acceptance criteria, they log the bug in a tracking tool (e.g., Jira, Azure DevOps). The defect is assigned the status New.

        2. Assigned: The QA Lead or Engineering Manager reviews the new defect and assigns it to the relevant developer or development squad for investigation.

        3. Open: The assigned developer starts analyzing the defect. At this stage, the developer determines whether the issue is valid:

            => Rejected: The developer believes the behavior matches the expected design or functional specification.

            => Duplicate: The issue is already logged under another existing defect ID.

            => Deferred: The defect is acknowledged as valid, but prioritized for a future release or sprint due to low severity or schedule constraints.

            => Not a Defect (Works as Designed): The observed behavior is intentional, or there was a misunderstanding of requirements.

            => If the defect is valid and in scope for the current cycle, the developer keeps the status as Open and writes code to fix it.

        4. Fixed: The developer implements the code change, runs unit tests, commits the fix, and deploys it to a test or preview environment. The status changes to Fixed.

        5. Pending Retest: The fix has been committed, but the build containing the fix has not yet been deployed to the QA environment. Once the build is deployed and ready for verification, the status moves to Retest.

        6. Retest: The QA engineer executes the exact reproduction steps against the deployed build to ensure the problem no longer occurs. They also execute surrounding regression tests to confirm no secondary breaks were introduced.

        7. Verified: The tester confirms that the issue is resolved and all related regression checks pass.

        8. Closed: After reaching the Verified stage, the QA engineer or Test Lead marks the ticket as Closed. The defect is completely resolved and its life cycle ends.

        9. Reopened: If the bug still reproduces during the Retest phase, the tester documents the failure, attaches new logs or screenshots, and sets the status to Reopened, sending it back to the developer.

@ Important scenario: How do you decide which test cases to automate?

    > Sample interview answer:

        “I decide which test cases to automate based on business risk, execution frequency, stability, complexity, and expected return on investment.

        First, I identify critical business workflows such as login, registration, payment, and data submission. Then I prioritize test cases that run frequently, especially regression tests, and those that need to be executed across multiple browsers or with different test data.

        I also check whether the feature is stable and whether the expected result can be verified reliably. I generally avoid automating one-time tests, highly unstable functionality, or tests that require subjective human judgment.

        Finally, I estimate the effort required to create and maintain the automation compared with the time saved during repeated execution. I prioritize high-value tests first and integrate them into CI/CD where appropriate.”

    > Suppose you are testing an e-commerce application:

        Test case | Automation decision | Reason

        Login with valid credentials | Automate	| Frequently used, critical workflow

        Login with invalid credentials | Automate | Repeatable validation and regression coverage

        Checkout and payment workflow | High priority to automate | Business-critical; use a safe test payment environment

        Search with many input combinations | Automate | Data-driven and repetitive

        Verify a minor one-time UI change | Depends	| Low repetition may not justify automation effort

        Explore whether a page feels intuitive | Primarily manual | Requires human judgment

@ What is Playwright?

    > Playwright is an open-source automation testing framework developed by Microsoft. It is mainly used for end-to-end testing of web applications.

    > It can automate browsers such as Chromium, Firefox, and WebKit.


@ Why do we use Playwright for automation testing?

    > Playwright provides many useful features:

        ✅ Cross-browser testing
        ✅ Supports Chromium, Firefox and WebKit
        ✅ Automatic waiting
        ✅ Parallel test execution
        ✅ API testing
        ✅ Network interception
        ✅ Screenshots and videos
        ✅ Built-in assertions
        ✅ Multiple tabs/pages support
        ✅ Mobile/device emulation
        ✅ Trace Viewer for debugging

    > Playwright automatically waits for the button to be ready before clicking.


@ Playwright vs Selenium?

    | Playwright                          | Selenium                                                  |
    | ----------------------------------- | --------------------------------------------------------- |
    | Developed by Microsoft              | Selenium project                                          |
    | Modern automation framework         | Older and widely adopted framework                        |
    | Auto-waiting built in               | Usually requires more explicit waits                      |
    | Supports Chromium, Firefox, WebKit  | Supports many browsers through WebDriver                  |
    | Supports API testing                | API testing usually requires additional tools             |
    | Parallel execution is built in      | Parallel execution usually uses Selenium Grid/TestNG etc. |
    | Supports multiple pages/tabs easily | Requires more handling                                    |
    | Has built-in trace viewer           | Debugging depends more on external tools                  |
    | Supports modern browser automation  | Very mature ecosystem                                     |
    ---------------------------------------------------------------------------------------------------


@ What browsers does Playwright support?

    > Playwright supports Chromium, Firefox, and WebKit, allowing us to perform cross-browser testing and allow us to use local browsers also.

    > You can configure them in playwright.config.ts

    > Supported channels: 'chrome', 'chrome-beta', 'chrome-dev', 'chrome-canary', 'msedge', 'msedge-beta', 'msedge-dev'.

    > "browserName: 'chromium'" represents Playwright's Chromium, "...devices['Desktop Chrome']" represents Desktop Chrome-like device settings and "channel: 'chrome'" represents Installed Google Chrome.

    > CODE SNIPPET:

        // playwright.config.ts

        import { chromium, firefox, webkit } from 'playwright';

        projects: [
            // Standard bundled browsers
            {
                name: 'chromium',
                use: { ...devices['Desktop Chrome'] } 
            },
            {
                name: 'firefox',
                use: { ...devices['Desktop Firefox'] }
            },
            {
                name: 'webkit',
                use: { ...devices['Desktop Safari'] } 
            },

            // 1. Local Google Chrome installed on your machine
            {
                name: 'Google Chrome',
                use: {
                    ...devices['Desktop Chrome'],
                    channel: 'chrome', // Uses locally installed Google Chrome
                }
            },

            // 2. Local Microsoft Edge installed on your machine
            {
                name: 'Microsoft Edge',
                use: {
                    ...devices['Desktop Edge'],
                    channel: 'msedge', // Uses locally installed Microsoft Edge
                }
            },

            // 3. Local Chrome Beta / Dev / Canary (if installed)
            {
                name: 'Chrome Beta',
                use: {
                    channel: 'chrome-beta',
                }
            },
        ]

@ How do you create and run your first Playwright test?

    > Create a file such as:

        >>  tests/login.spec.ts

    > Then:

        >>  import { test, expect } from '@playwright/test';

            test('Open website', async ({ page }) => {
                await page.goto('https://example.com');
                await expect(page).toHaveTitle('Example Domain');
            });

    > Run it:

        >>  npx playwright test

    > Run a specific file:

        >>  npx playwright test tests/login.spec.ts

    > Run in headed mode:

        >>  npx playwright test tests/login.spec.ts --headed

    > Debug mode:

        >>  npx playwright test tests/login.spec.ts --debug


@ What is playwright.config.ts?

    > playwright.config.ts is the central configuration file where we define settings such as browser, base URL, timeout, retries, workers, screenshots, videos, traces, and reporters.

    > Browser: Specifies which browser Playwright should run the tests in.

        >>  {
                name: 'chromium',
                use: { browserName: 'chromium' }
            }

        >> To run: npx playwright test --project=chromium

    > Base URL: Defines the common URL of your application.

        >>  baseURL: 'https://example.com'

    > Timeout: Defines how long Playwright should wait for a test or action.

        >>  timeout: 30 * 1000 // Each test can run for a maximum of 30 seconds.

        >>  actionTimeout: 10 * 1000 // Actions like click/fill can wait up to 10 seconds.

    > Retries: Defines how many times a failed test should be retried.

        >>  retries: 2

    > Workers: Defines how many tests can run in parallel.

        >>  workers: 4

    > Screenshots: Take a screenshot when a test fails.

        >>  screenshot: 'off' (or) 'on' (or) 'only-on-failure'

    > Videos: Record the test execution, especially useful for debugging failures.

        >>  video: 'off' (or) 'on' (or) 'retain-on-failure'

    > Trace: Capture detailed execution information when a test is retried.

        >>  In config file:- trace: 'on-first-retry'

        >>  You can view it using:- npx playwright show-trace trace.zip

    > Reporter: Reporter controls how Playwright displays and generates test results.

        >> In config file:- reporter: 'html' (or) reporter: [['list'], ['html']]
    
        >> After running tests:- npx playwright test

        >> Open the report:- npx playwright show-report

    > Test Directory: Tells Playwright where to find the test files.

        >> testDir: './tests'

    > CODE SNIPPET:

        import { defineConfig, devices } from '@playwright/test';

        export default defineConfig({

            // Test directory
            testDir: './tests',

            // Test timeout
            timeout: 30 * 1000,

            // Retry failed tests
            retries: 2,

            // Parallel workers
            workers: 4,

            // Test reporter
            reporter: 'html',

            // Browser projects
            projects: [
                {
                    name: 'chromium',
                    use: {
                        ...devices['Desktop Chrome'],

                        baseURL: 'https://example.com',

                        // Action timeout
                        actionTimeout: 10 * 1000,

                        // Screenshot
                        screenshot: 'only-on-failure',

                        // Video
                        video: 'retain-on-failure',

                        // Trace
                        trace: 'on-first-retry'
                    }
                },
                {
                    name: 'firefox',
                    use: {
                        browserName: 'firefox',
                        baseURL: 'https://example.com'
                    }
                }
            ]
        });


@ What is the purpose of test() and expect()?

    > These are two of the most important Playwright Test APIs.

    > test(): defines a test case and What am I testing?

        >>  test('Login functionality', async ({ page }) => {
                await page.goto('/login');
            });

    > expect(): is used for assertions and it verifies whether the actual result matches what we expect.

        >>  await expect(page).toHaveTitle('Dashboard');
        >>  await expect(page.getByRole('button', { name: 'Login' })).toBeVisible();
        >>  await expect(page.locator('#username')).toHaveValue('admin');



//////////////////////////////////// Browser vs Context vs Page ////////////////////////////////////

@ Browser → BrowserContext → Page

    > The relationship is:

        Browser
        ↓
        BrowserContext
        ↓
        Page

    > Think of it like:

        Browser = The whole browser application
        Context = A separate browser session
        Page = A tab inside that session


@ What is Browser?

    > A Browser represents the actual browser engine.

    > Playwright supports:

        >> Chromium
        >> Firefox
        >> WebKit

    > Here, browser represents a running Chromium browser.

    > You can then create contexts inside it.

    > Simple example:

        >> const browser = await chromium.launch({ headless: false });


@ What is BrowserContext?

    > A BrowserContext is an isolated browser session.

    > Each context has its own:

        >> Cookies
        >> Local storage
        >> Session storage
        >> Cache
        >> Login/session information

    > You can create multiple independent contexts.

    > Flow chart:

        Browser
        │
        ├── Context 1 → User A
        │
        └── Context 2 → User B

    > Simple example:

        >> const context = await browser.newContext();


@ What is Page?

    > A Page represents a browser tab.

    > You can also create multiple pages in the same context.

    > Flow chart:

        Browser
        │
        └── Context
            │
            ├── Page 1 → Tab 1
            └── Page 2 → Tab 2

    > Simple example:

        >> const page1 = await context.newPage();
        >> const page2 = await context.newPage();


@ Table:

    | Component             | Simple meaning                         |
    | --------------------- | -------------------------------------- |
    | **Browser**           | Browser instance                       |
    | **BrowserContext**    | Isolated browser session               |
    | **Page**              | Browser tab                            |
    | **Browser → Context** | One browser can have multiple sessions |
    | **Context → Page**    | One session can have multiple tabs     |
    ------------------------------------------------------------------


@ Complete Example:

    > Code snippet:

        import { chromium } from '@playwright/test';
        const browser = await chromium.launch();
        const context = await browser.newContext();
        const page = await context.newPage();
        await page.goto('https://example.com');
        await browser.close();

    > Flow:

        chromium.launch()
        ↓
        Browser
        ↓
        browser.newContext()
        ↓
        BrowserContext
        ↓
        context.newPage()
        ↓
        Page
        ↓
        page.goto()


@ Interview Questions:

    Q1. Can one Browser have multiple BrowserContexts?

        Yes.

    Q2. Can one BrowserContext have multiple Pages?

        Yes, they represent two tabs in the same browser session.

    Q3. Why is BrowserContext useful in testing?

        It provides test isolation. Each test can have its own cookies, storage, authentication state, and session without affecting other tests.

    Q4. Is BrowserContext the same as Incognito mode?

        Conceptually, it is similar in terms of isolation, but Playwright contexts are specifically designed as lightweight isolated browser sessions for automation. You normally use:

        const context = await browser.newContext();

        rather than trying to configure an incognito option.



//////////////////////////////////// Locators ////////////////////////////////////

@ Playwright locators:

    > Playwright Locator methods used to find elements on a web page. They are very commonly asked in interviews.

    > I prefer user-facing locators such as getByRole(), getByLabel(), and getByText() because they are generally more readable and resilient. I use getByTestId() when a stable test ID is intentionally provided, and locator() when I need CSS/XPath or more complex element selection.

    > Preference order:

        getByRole()
            ↓
        getByLabel()
            ↓
        getByPlaceholder()
            ↓
        getByText()
            ↓
        getByTestId()
            ↓
        locator()

    > Table:

        | Method               | Simple meaning                      |
        | -------------------- | ----------------------------------- |
        | `locator()`          | Find element using CSS/XPath        |
        | `getByRole()`        | Find element by its accessible role |
        | `getByText()`        | Find element by visible text        |
        | `getByLabel()`       | Find form element by its label      |
        | `getByPlaceholder()` | Find input using placeholder text   |
        | `getByTestId()`      | Find element using `data-testid`    |


@ List of locator methods:

    > page.locator(): Used to locate an element using CSS selector, XPath, or other supported selector syntax.

        >> page.locator('.login-btn')

    > page.getByRole(): finds an element based on what the element represents to the user.

        >> Example roles such as button, textbox, link, checkbox, heading, radio and combobox.

        >> page.getByRole('button', { name: 'Login' })

    > getByText(): finds an element by the text displayed on the page.

        >> page.getByText('Login successful')

    > getByLabel(): finds a form control using its associated label.

        >> page.getByLabel('Email')

    > getByPlaceholder(): finds an input using its placeholder.

        >> page.getByPlaceholder('Enter your email')

    > page.getByTestId(): finds an element using a dedicated test ID means data-testid attribute.

        >> age.getByTestId('login-button')



//////////////////////////////////// Trigger Event Methods ////////////////////////////////////

@ What is auto-waiting:

    > Auto-waiting means Playwright automatically waits for an element to meet the necessary conditions before performing an action, such as clicking a button.

    > Playwright waits for the button to be actionable, including being visible, stable, enabled, and able to receive events.


@ List of methods:

    > click(): Click the element.

        >>  await loginButton.click();

    > fill(): Fills an input with text. It is usually preferred for normal form filling

        >> await username.fill('John');

    > type(): is mainly useful when you specifically want keyboard-like typing behavior.

        >> await username.type('John');

    > press(): Press a keyboard key while the element is focused.

        >> await username.press('ArrowDown');

    > check(): Checks a checkbox or radio button.

        >> await checkbox.check();

@ Drag and drop:

    > Using dragTo() — Recommended:

        >> In Playwright, you can perform drag and drop using dragTo() or by using mouse actions for more complex scenarios.

        >> CODE SNIPPET:

            import { test, expect } from '@playwright/test';

            test('Drag and drop an item', async ({ page }) => {
                await page.goto('https://example.com');

                const source = page.locator('#source');
                const target = page.locator('#target');

                await source.dragTo(target);

                await expect(target).toContainText('Dropped item');
            });

        >> How it works:

            > source — the element you want to drag.
            > target — the element where you want to drop it.
            > dragTo() — performs the drag-and-drop action.

    > Using mouse actions:

        >> Use this approach when dragTo() doesn't work or you need more control over the mouse movement.

        >> CODE SNIPPET:

            const source = page.locator('#source');
            const target = page.locator('#target');

            const sourceBox = await source.boundingBox();
            const targetBox = await target.boundingBox();

            if (!sourceBox || !targetBox) {
                throw new Error('Source or target element not found');
            }

            await page.mouse.move(
                sourceBox.x + sourceBox.width / 2,
                sourceBox.y + sourceBox.height / 2
            );

            await page.mouse.down();

            await page.mouse.move(
                targetBox.x + targetBox.width / 2,
                targetBox.y + targetBox.height / 2,
                { steps: 10 }
            );

            await page.mouse.up();


        >> steps: 10 moves the mouse gradually toward the target.

    > How do you drag an element to the left side of a target?

        >> If the drop zone is on the left side, calculate a position inside the target near its left edge.

        >> CODE SNIPPET:

            const source = page.locator('#source');
            const target = page.locator('#target');

            await source.dragTo(target, {
                targetPosition: { x: 5, y: 20 }
            });


        >> Here, x: 5 means five pixels from the target's left edge, and y: 20 means 20 pixels from its top edge.

    > Interview answer: “I use Playwright's dragTo() method for standard drag-and-drop operations. If the application requires a specific drop position or custom mouse movement, I use boundingBox() with page.mouse.move(), mouse.down(), and mouse.up().”

//////////////////////////////////// Custom Fixtures ////////////////////////////////////

@ Definition:

    > In Playwright, custom fixtures allow you to create reusable setup and teardown logic that can be shared across multiple spec files.

    > For example, you can create a custom fixture that automatically opens your application and provides a logged-in page to your tests.


@ Create a custom fixture:

    > Project structure:

        playwright-project/
        ├── fixtures/
        │   └── custom-fixtures.ts
        ├── tests/
        │   └── dashboard.spec.ts
        └── playwright.config.ts

    > Define fixtures 

        // fixtures/custom-fixtures.ts
        >>  import { test as base, expect, Page } from '@playwright/test';

            type MyFixtures = {
                appPage: Page;
            };

            export const test = base.extend<MyFixtures>({
                appPage: async ({ page }, use) => {
                    // Setup: runs before the test
                    await page.goto('https://example.com');

                    // Provide the page to the test
                    await use(page);

                    // Teardown: runs after the test
                    console.log('Test completed');
                },
            });

            export { expect };

    > How it works:

        >> base.extend() — creates a custom fixture.
        >> appPage — the name of your custom fixture.
        >> page — Playwright's built-in page fixture.
        >> await use(page) — provides the page to the test.
        >> Code after await use(page) — runs during teardown.


@ Fixture execution flow:

    Test starts
    ↓
    Fixture setup
    (Navigate to application)
    ↓
    await use(page)
    (Run the test using appPage)
    ↓
    Fixture teardown
    (Execute cleanup code)


@ Exercise: Custom fixture with automatic login:-

    > You can also create a fixture that logs in before every test.

        >>  import { test as base, expect, Page } from '@playwright/test';

                    await page.waitForURL('**/dashboard');

            });

            export { expect };

    > Use it in your spec:

        >>  import { test, expect } from '../fixtures/custom-fixtures';

                await expect(loggedInPage).toHaveURL(/dashboard/);
            });        



//////////////////////////////////// Authentication & Storage State ////////////////////////////////////

@ Interview Answer:

    > In Playwright, authentication and storage state let you log in once and reuse the authenticated session across multiple tests instead of logging in before every test.

    > I use Playwright's storageState to reuse authentication across tests. First, I create a setup test that logs into the application and saves cookies and local storage to a JSON file. Then I configure the main test project to use that file. Playwright creates authenticated browser contexts, allowing tests to access protected pages without repeating the login process. I keep the authentication file out of version control because it can contain sensitive session data.

    > If the session is invalid or expired, your application may redirect to the login page. In that case, check whether the setup login succeeded, whether the state file was created, and whether the authentication session has expired.

    > Q&A:

        >> What is storage state?	
            => A saved snapshot of browser authentication data.

        >> What does it save?	
            => Cookies and local storage; IndexedDB can also be included when configured and supported.

        >> Why use it?	
            => Avoid repeating login steps in every test.

        >> Does it save the whole browser?	
            => No. It saves selected storage data, not the entire browser session.

        >> Does it include sessionStorage by default?	
            => No. It requires a separate implementation if your app relies on it.

        >> Is the same session shared between tests?	
            => Tests can start with the same saved state, but normally use separate browser contexts.

        >> What if authentication expires?	
            => Reauthenticate and regenerate the storage state.


@ 1. Understand the flow: 

    1. Login setup
    (Open app → Enter credentials → Log in)
        ↓
    2. Save storage state
    (Save cookies and local storage to auth.json)
        ↓
    3. Reuse the session
    (Tests load auth.json and access protected pages)


@ 2. Project structure:

    > Create these files in your Playwright project:

        playwright-project/
        ├── tests/
        │   └── dashboard.spec.ts
        ├── tests-examples/        (optional)
        ├── playwright/
        │   └── .auth/
        │       └── user.json      (generated)
        ├── playwright.config.ts
        └── package.json

    > The user.json file is generated by Playwright and contains authentication data. Do not commit it to Git, because it may contain session credentials. So, Add this to .gitignore:

        >> playwright/.auth/


@ 3. Create playwright.config.ts

    > This configuration runs the login setup first, then runs your tests using the saved session.

        >>  import { defineConfig, devices } from '@playwright/test';

            const authFile = 'playwright/.auth/user.json';

            export default defineConfig({
                testDir: './tests',

                use: {
                    baseURL: 'https://your-app.com',
                    trace: 'on-first-retry',
                },

                projects: [
                    {
                        name: 'setup',
                        testMatch: /auth\.setup\.ts/,
                    },
                    {
                        name: 'chromium',
                        use: {
                            ...devices['Desktop Chrome'],
                            storageState: authFile,
                        },
                        dependencies: ['setup']
                    }
                ]
            });


@ 4. Create setup.ts and gitignore files:

    > This file logs in and saves the authenticated browser state.

    > Update the labels, button name, login URL, and dashboard URL pattern to match your application. The ! tells TypeScript to treat the environment variable as defined; it does not check whether the variable actually exists.

    > Create tests/auth.setup.ts:

        >>  import { test as setup, expect } from '@playwright/test';
            import fs from 'node:fs';
            import path from 'node:path';

            const authFile = 'playwright/.auth/user.json';

            setup('authenticate', async ({ page }) => {
                // Create the folder if it doesn't exist
                fs.mkdirSync(path.dirname(authFile), { recursive: true });

                // Open the login page
                await page.goto('/login');

                // Enter credentials
                await page.getByLabel('Email').fill(process.env.E2E_USERNAME!);

                await page.getByLabel('Password').fill(process.env.E2E_PASSWORD!);

                // Submit the login form
                await page.getByRole('button', { name: 'Sign in' }).click();

                // Verify that login succeeded
                await expect(page).toHaveURL(/dashboard/);

                // Save cookies and local storage
                await page.context().storageState({ path: authFile });
            });

    > Set the credentials in your environment before running the tests. Use dedicated test credentials, not your personal account:

    > Create .env file:

        >>  $env:E2E_USERNAME="your-test-user"
            $env:E2E_PASSWORD="your-test-password"


@ 5. Create tests/dashboard.spec.ts:

    > Now write a test that uses the saved login state. You do not need to enter credentials again.

    > Because the Chromium project in playwright.config.ts specifies storageState, each test receives a new browser context initialized with the saved authentication state.

//////////////////////////////////// API Testing ////////////////////////////////////

@ Important API testing concepts:

    > HTTP methods: Define the operation performed by an API.	
        >> GET, POST, PUT, PATCH, DELETE

    > Status codes:	Indicate the result of an HTTP request.	
        >> 200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 500 Internal Server Error

    > Headers: Provide additional request or response information.	
        >> Content-Type: application/json

    > Request body: Data sent to the server.	
        >> Sending name and email during registration.

    > Response body: Data returned by the server.	
        >> User details in JSON format.

    > Authentication: Verifies who the user is.	
        >> Bearer token, API key, OAuth

    > Authorization: Determines what the user is allowed to do.	
        >> A normal user cannot delete an admin account.

    > Schema validation: Checks response structure and data types.	
        >> id should be a number and email a string.
    
    > Negative testing:	Checks how APIs handle invalid requests.	
        >> Missing required email returns 400.

    > Response time: Measures how long the API takes to respond.	
        >> Verify a request finishes within an acceptable threshold.


@ HTTP methods you must know:

    > GET: Retrieve data	
        >> Get all users

    > POST: Create data or trigger an operation	
        >> Register a user

    > PUT: Replace a resource	
        >> Replace a user's profile

    > PATCH: Partially update a resource	
        >> Update only the user's name

    > DELETE: Delete a resource	
        >> Delete a user


@ Important HTTP status codes:

    > 200: OK => Data retrieved successfully

    > 201: Created => User created successfully

    > 204: No Content => Successful deletion with no response body

    > 400: Bad Request => Invalid request data

    > 401: Unauthorized	=> Missing or invalid authentication

    > 403: Forbidden => User lacks permission

    > 404: Not Found => Requested resource doesn't exist

    > 409: Conflict => Duplicate email or conflicting resource state

    > 422: Unprocessable Content => Request content fails validation, depending on API design

    > 429: Too Many Requests => Rate limit exceeded

    > 500: Internal Server Error => Unexpected server failure


@ What should you validate in API testing?

    > Whenever you test an API, consider these checks:

        1. Status code: Is the correct HTTP status returned?

        2. Response body: Are the returned values correct?

        3. Headers: Is the content type correct? Are required security or caching headers present?

        4. Schema: Do fields have the expected names and data types?

        5. Authentication: Does the API reject missing or invalid credentials?

        6. Authorization: Can users access only permitted resources?
        
        7. Negative cases: What happens with missing, invalid, or malformed input?
        
        8. Data integrity: Was the data correctly created, updated, or deleted?

        9. Response time: Is the response within the agreed performance threshold?

        10. Error handling: Are errors handled consistently without exposing sensitive information?


@ Important API testing scenarios: 

    > Consider a user registration API.
    
    > List of scenarios	with expected result.

        >> Register with valid data	=> User is created

        >> Register with an existing email => Duplicate registration is rejected

        >> Submit without an email => Validation error

        >> Submit an invalid email => Validation error

        >> Send a request without authentication, if required => 401

        >> Access a resource without permission => 403

        >> Request a nonexistent user => 404

        >> Send an unsupported HTTP method => Usually 405, if defined by the API

        >> Submit a very large payload => Handled according to documented size limits

        >> Send many requests rapidly => Rate limiting is applied if configured


@ API testing vs. UI testing:

    > API testing	
        
        >> Tests endpoints and backend behavior directly.	
        
        >> Usually faster for validating business logic.	
        
        >> Checks status codes, headers, and response data.	
        
        >> Playwright's request fixture is useful.	

    > UI testing:
        
        >> Tests the application through its user interface.
        
        >> Validates visible behavior and user interactions.
        
        >> Checks buttons, forms, navigation, and displayed results.
        
        >> Playwright's page fixture is useful.


@ API requests using 'request' fixture:

    > Here are simple Playwright API testing examples using the built-in request fixture for GET, POST, PUT, PATCH, and DELETE with TypeScript.
    
    > Assume the API endpoint is https://api.example.com/users 

    > 1. GET — Retrieve users:

        >>  import { test, expect } from '@playwright/test';

            test('GET - Get user', async ({ request }) => {
                const response = await request.get(
                    'https://api.example.com/users/1'
                );

                expect(response.status()).toBe(200);

                const body = await response.json();

                expect(body.id).toBe(1);
                expect(body.name).toBeTruthy();
            });

    > 2. POST — Create a new user:

        >>  test('POST - Create user', async ({ request }) => {
                const response = await request.post(
                    'https://api.example.com/users',
                    {
                        data: {
                            name: 'John',
                            email: 'john@example.com'
                        }
                    }
                );

                expect(response.status()).toBe(201);

                const body = await response.json();

                expect(body.name).toBe('John');
                expect(body.email).toBe('john@example.com');
                expect(body.id).toBeTruthy();
            });

    > 3. PUT — Replace an existing user:

        >>  PUT generally replaces the resource representation, so include all required fields.

        >>  test('PUT - Replace user', async ({ request }) => {
                const response = await request.put(
                    'https://api.example.com/users/1',
                    {
                        data: {
                            name: 'John Smith',
                            email: 'johnsmith@example.com'
                        }
                    }
                );

                expect(response.status()).toBe(200);

                const body = await response.json();

                expect(body.name).toBe('John Smith');
                expect(body.email).toBe('johnsmith@example.com');
            });

    > 4. PATCH — Update specific fields:

        >>  PATCH updates only the specified fields, depending on the API's implementation.

        >>  test('PATCH - Update user email', async ({ request }) => {
                const response = await request.patch(
                    'https://api.example.com/users/1',
                    {
                        data: {
                            email: 'newemail@example.com'
                        }
                    }
                );

                expect(response.status()).toBe(200);

                const body = await response.json();

                expect(body.email).toBe('newemail@example.com');
            });

    > 5. DELETE — Delete a user

        >>  A successful DELETE can return 204 No Content or another documented success status. 
        
        >>  If the response is 204, don't try to parse a JSON response body.

        >>  test('DELETE - Delete user', async ({ request }) => {
                const response = await request.delete(
                    'https://api.example.com/users/1'
                );

                expect(response.status()).toBe(204);
            });

    > HTTP methods with possible success status:
        
        >> GET => request.get(url) => 200
        
        >> POST => request.post(url, { data }) => 201
        
        >> PUT => request.put(url, { data }) => 200 or 204
        
        >> PATCH => request.patch(url, { data }) => 200 or 204
        
        >> DELETE => request.delete(url) => 200 or 204


@ Intercept and mock API requests:

    > Use page.route() to intercept requests and provide mock responses, or modify and block requests.

    > Common methods:
        - route.fulfill() — returns a mock response.
        - route.continue() — sends the request onward, optionally modified.
        - route.abort() — blocks the request.

    > SCENARIO: Test UI behavior with predictable API data without depending on a real backend response.

    > CODE SNIPPET: 

        >>  test('dynamically toggle route mocking on and off', async ({ page }) => {
                const handler = async (route) => {
                    await route.fulfill({
                        status: 200,
                        body: JSON.stringify({ status: 'MOCKED' }),
                    });
                };

                // Apply mock handler
                await page.route('**/api/status', handler);
                await page.goto('https://example.com/status');
                await expect(page.getByTestId('status-box')).toHaveText('MOCKED');

                // Remove the mock; subsequent requests hit the real network
                await page.unroute('**/api/status', handler);
                await page.reload();
                await expect(page.getByTestId('status-box')).toHaveText('LIVE');
            });



//////////////////////////////////// Database Testing ////////////////////////////////////

@ Automating Database Testing with Playwright:

    > Playwright is mainly used for browser automation and API testing. It does not have a built-in database testing API, but you can connect to a database using Node.js libraries and verify database records during your tests.

    > For example, you can use Playwright with MySQL, PostgreSQL, or SQL Server.


@ How does database testing work?

    > Suppose you register a new user through your application.

            Playwright Test
        (Enter user details and click Register)
                ↓
        Frontend → Backend API
        (Angular / React → Node.js / Express)
                ↓
            Database
        (MySQL stores the new user)

    > Playwright verifies the saved record using a database query.


@ Install the MySQL package:

    > If you're using TypeScript with Playwright Test:

        >>  npm install mysql2
        >>  npm install --save-dev @types/node  

    > mysql2 is a Node.js library that allows your test code to connect to MySQL.


@ Create a database connection:

    > Create a file named db.ts.

        >>  import mysql from 'mysql2/promise';
            export const connection = await mysql.createConnection({
                host: process.env.DB_HOST,
                user: process.env.DB_USER,
                password: process.env.DB_PASSWORD,
                database: process.env.DB_NAME
            });

    > Store your database credentials in environment variables instead of hardcoding them in your test.


@ Fetch data from the database:

    > Suppose you have a users table.

        id	name	email
        1	John	john@example.com
        2	Mike	mike@example.com

    > You can query the database:

        >>  import { connection } from './db';
            const [rows] = await connection.execute(
                'SELECT * FROM users WHERE email = ?',
                ['john@example.com']
            );
            console.log(rows);

    > The ? placeholder safely passes the email as a parameter.


@ Complete example: UI + Database testing

    > Suppose your application has a registration form.

        >> import { test, expect } from '@playwright/test';
            import { connection } from './db';

            test('Register user and verify database', async ({ page }) => {
                const email = `john${Date.now()}@example.com`;

                await page.goto('http://localhost:4200/register');

                await page.getByLabel('Name').fill('John');
                await page.getByLabel('Email').fill(email);

                await page.getByRole('button', { name: 'Register' }).click();

                await expect(page.getByText('Registration successful')).toBeVisible();

                const [rows] = await connection.execute(
                    'SELECT * FROM users WHERE email = ?',
                    [email]
                );

                const users = rows as { name: string; email: string }[];

                expect(users).toHaveLength(1);
                expect(users[0].name).toBe('John');
                expect(users[0].email).toBe(email);
            });

    > What are we verifying?
        - The user exists.
        - Exactly one matching record is returned.
        - The user's name and email match the expected values.

    > This test verifies both the UI behavior and the database result.

    > Close the database connection after the tests finish, using an appropriate test-suite teardown such as test.afterAll().

        >>  afterAll(async () => {
                await connection.end(); // Or connection.disconnect() / mongoose.connection.close()
            });


@ What database operations can you test?

    > TABLE:
        Operation	SQL example	                What to verify
        Create	    INSERT INTO users ...	    Record was created
        Read	    SELECT * FROM users	        Correct data was returned
        Update	    UPDATE users SET ...	    Changes were saved
        Delete	    DELETE FROM users WHERE ...	Record was removed

    > For destructive operations such as UPDATE and DELETE, use a dedicated test database and test records.   


@ Important interview questions

    Q1. Can Playwright connect directly to a database?
        Playwright doesn't provide a built-in database client. We can use Node.js database drivers, such as mysql2, to execute queries and validate database records.

    Q2. Why do we perform database testing?
        To verify data integrity, confirm that UI/API operations are persisted correctly, and ensure that database records match the expected results.

    Q3. Should every Playwright test query the database?
        No. Most UI tests should verify user-visible behavior. Database queries are useful when we specifically need to validate persistence or backend data integrity.

    Q4. What is the difference between API testing and database testing?
        - API testing: Verifies HTTP requests, status codes, response headers, and response data.
        - Database testing: Verifies stored records, relationships, constraints, and data integrity.

    > Interview summary: Playwright can be integrated with database drivers such as mysql2 to validate records created, updated, or deleted through the UI or API. This enables end-to-end verification across the frontend, backend, and database.



//////////////////////////////////// Accessiblity Testing ////////////////////////////////////

@ AxeBuilder methods in Playwright:

    > AxeBuilder is provided by @axe-core/playwright. It helps you configure and run automated accessibility scans on a webpage. Its methods are chainable, so you can configure the scan and then call .analyze() to execute it.

    > Installation and basic setup:

        >>  npm install -D @axe-core/playwright

        >>  import { test, expect } from '@playwright/test';
            import AxeBuilder from '@axe-core/playwright';

            test('accessibility scan', async ({ page }) => {
                await page.goto('/');
                const results = await new AxeBuilder({ page }).analyze();
                expect(results.violations).toEqual([]);
            });

    > Main methods at a glance:

        Method          |   Purpose
        include()	    |   Scan specific page regions
        exclude()	    |   Exclude specific page regions
        withTags()	    |   Run rules associated with selected tags, such as WCAG criteria
        withRules()	    |   Run only specific accessibility rules
        disableRules()	|   Skip specific accessibility rules
        options()	    |   Pass configuration options directly to axe-core
        analyze()	    |   Execute the scan and return results


@ List of AxeBuilder methods:

    > include() — scan a specific section
        >>  const results = await new AxeBuilder({ page }).include('#login-form').analyze();

    > exclude() — skip a specific section
        >>  const results = await new AxeBuilder({ page }).exclude('#third-party-widget').analyze();

    > withTags() — scan rules associated with WCAG tags
        >>  const results = await new AxeBuilder({ page }).withTags(['wcag2a','wcag2aa','wcag21a','wcag21aa']).analyze();

    > withRules() — run specific rules
        >>  const results = await new AxeBuilder({ page }).withRules(['image-alt','button-name','link-name','label']).analyze();

    > disableRules() — skip selected single or multiple rules
        >>  const results = await new AxeBuilder({ page }).disableRules(['color-contrast']).analyze();

    > options() — customize axe-core settings and options() can override rule selection configured with withRules() or withTags()
        >>  const results = await new AxeBuilder({ page }).options({ resultTypes: ['violations'] }).analyze();

    > analyze() — execute the accessibility scan
        >>  const results = await new AxeBuilder({ page }).analyze();
            console.log('Violations:', results.violations); // returns list of violations
            console.log('Passed checks:', results.passes); // returns list of passes
            console.log('Needs review:', results.incomplete); // returns list of incomplete results
            console.log('Not applicable:', results.inapplicable); // returns list of not applicable things

    > violations - return the list of violations if captured in page
        >>  expect(results.violations).toEqual([]);
            for (const violation of results.violations) {
                console.log('Rule:', violation.id);
                console.log('Impact:', violation.impact);
                console.log('Description:', violation.description);
                console.log('Affected elements:', violation.nodes.map(
                    node => node.target
                ));
            }


@ What should you test?

    > Keyboard accessibility: Can users navigate with Tab, Shift+Tab, Enter, Space, and Escape without a mouse?

    > Screen reader support: Do buttons, inputs, images, and dialogs have meaningful accessible names and roles?

    > Visual accessibility: Are text and controls readable, with sufficient color contrast and visible focus indicators?

    > Automated accessibility rules: Are there detectable issues such as missing form labels, invalid ARIA attributes, or insufficient contrast?

    > The commonly used standard is WCAG (Web Content Accessibility Guidelines). WCAG 2.2 Level AA is a useful target for many web applications.
