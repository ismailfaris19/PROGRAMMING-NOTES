////////////////////////// System Design //////////////////////////

@ Suppose an interviewer says:

    > "Design an e-commerce application like Amazon."

    > They don't expect you to immediately write Angular components or Express controllers.


@ They want to know:

    > How will all the pieces of the application work together when thousands/millions of users use it?


@ For example:

    > This is System Design.

                    USER
                     |
                     ↓
                  Angular
                  Frontend
                     |
                     ↓
                HTTP / HTTPS
                     |
                     ↓
              Node.js + Express
                 Backend
                     |
          ┌──────────┼──────────┐
          ↓          ↓          ↓
       MySQL      Redis      File Storage
       Database    Cache        S3



////////////////////////// HLD vs LLD //////////////////////////

@ HLD — High-Level Design:

    > HLD answers: "What are the major components and how do they communicate?"

    > Example:
        Angular
        ↓
        Load Balancer
        ↓
        Node.js / Express
        ↓
        ┌───────────────┐
        │               │
        MySQL          Redis

    > We discuss:
        >> Architecture
        >> Services
        >> Databases
        >> APIs
        >> Load balancing
        >> Caching
        >> Scalability
        >> Authentication
        >> Communication between services
        >> Message queues
        >> Deployment
        >> Generally don't write detailed classes/functions here.


@ LLD — Low-Level Design:

    > LLD answers: "How exactly will we implement those components?"

    > Example:
        UserController
            ↓
        UserService
            ↓
        UserRepository
            ↓
        MySQL

    > We discuss:
        >> Classes
        >> Interfaces
        >> Functions
        >> Models
        >> Database tables
        >> Relationships
        >> API request/response
        >> Validation
        >> Design patterns
        >> Error handling
        >> Code structure



////////////////////////// Gathering Requirements //////////////////////////

@ Functional requirements:

    > What should the system do?

    > Functional = WHAT the system does

    > For our application:

        1. User registration
        2. User login
        3. Create task
        4. View tasks
        5. Update task
        6. Delete task
        7. Mark task completed


@ Non-functional requirements:

    > How should the system behave?

    > Non-functional = HOW well the system does it

    > For example:

        1. Secure
        2. Fast
        3. Scalable
        4. Available
        5. Maintainable

////////////////////////// LLD Example //////////////////////////

@ Backend Architecture:

    > Instead of putting everything inside one file: server.js

    > Layers: 

        Backend
        │
        ├── controllers
        │
        ├── services
        │
        ├── repositories
        │
        ├── models
        │
        ├── routes
        │
        ├── middleware
        │
        └── config

    > Flow: 

        POST /tasks
            ↓
        Route
            ↓
        Controller
            ↓
        Service
            ↓
        Repository
            ↓
        MySQL


@ Deep dive-in for LLD flow:

    > API endpoint: 
        >>  POST /api/tasks

    > Route: 
        >>  router.post('/tasks', taskController.createTask);

    > Controller: 
        >>  const createTask = async (req, res) => {
                const task = await taskService.createTask(req.body);
                res.status(201).json(task);
            };

    > Service: 
        >>  const createTask = async (data) => {
                // business logic
                return taskRepository.create(data);
            };

    > Repository:
        >>  const create = async (data) => {
                // Insert into MySQL
                const [result] = await db.execute(`INSERT INTO tasks (title, [data.title, data.description]);
                return result;
            };

////////////////////////// Scalability & Redis //////////////////////////

@ Scalability:

    > What if one Node server cannot handle all requests?
        >>  The Load Balancer distributes requests.

    > We can have multiple backend instances:

        >>       Angular
                    |
                    ↓
              Load Balancer
             /      |      \
            ↓       ↓       ↓
         Node     Node     Node
         API      API      API
            \       |       /
             \      |      /
                  MySQL

        >>  This is horizontal scaling.

            Request 1 → Server 1
            Request 2 → Server 2
            Request 3 → Server 3
            Request 4 → Server 1


@ Redis:

    > Suppose users repeatedly request:
        >>  GET /api/tasks

    > Every request goes to MySQL. With many requests, database load increases.
        >>  User -> Node -> MySQL

    > Here Redis play a game and Redis is commonly used as a cache.
        >>  User
            ↓
            Node
            ↓
            Redis
            ↓
            Data available?
            ├── YES → return data
            │
            └── NO
                ↓
                MySQL
                ↓
                Redis
                ↓
                User

    

////////////////////////// INTERVIEW QUESIONS //////////////////////////

@ Suppose interviewer says:

    > Design a task management application.


@ HLD Answer: 

    > I'll use Angular for the frontend and Node.js with Express for the REST API. MySQL will store users and tasks. For scalability, I can run multiple Node instances behind a load balancer. Redis can be introduced for frequently accessed data. JWT can handle authentication.

    >   Angular
        ↓
        Load Balancer
        ↓
        Node/Express
        ↓
        Redis
        ↓
        MySQL


@ LLD Answer:

    > Then they may ask:
        >> How would you implement task creation?

    >   Route
        ↓
        Controller
        ↓
        Service
        ↓
        Repository
        ↓
        MySQL

////////////////////////// RULE TO REMEMBER //////////////////////////

@ When you see a System Design question, don't immediately start coding.

             REQUIREMENTS
                  ↓
             ARCHITECTURE
                  ↓
              COMPONENTS
                  ↓
              DATA FLOW
                  ↓
             DATABASE DESIGN
                  ↓
                 APIs
                  ↓
              SCALABILITY
                  ↓
                SECURITY
                  ↓
             FAILURE CASES
